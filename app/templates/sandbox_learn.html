Learn: SQL injection and how to stop it

A quick, practical guide. Read this, then fix the real findings in the sandbox.

1. What is SQL injection?

A web page often builds a database query out of whatever you type. SQL injection is when that input is treated as part of the command instead of as plain data, so an attacker can change what the query does.

Take a member-lookup page that builds its query like this:

query = "SELECT * FROM members WHERE member_id = '" + user_input + "'"

If someone types 1, the query asks for member 1 — fine. But if they type ' OR '1'='1, the query becomes: 

SELECT * FROM members WHERE member_id = '' OR '1'='1'

'1'='1' is always true, so the database returns every member's record — names, national IDs, phone numbers, balances. That is a data-protection breach, and it's why this matters for a SACCO or microfinance.

2. Why it happens

The root cause is always the same: the value is glued directly into the SQL string (string concatenation, f"..." f-strings, .format(), or % formatting). The database has no way to tell "data the user typed" from "commands the programmer wrote".

3. The fix: parameterized queries

The fix is to send the query and the values separately. You put a placeholder in the query and hand the value to the database driver, which keeps it as data — it can never become part of the command. This is called a parameterized query or prepared statement.

Python (sqlite3 / most drivers):

# vulnerable
cursor.execute("SELECT * FROM members WHERE member_id = '" + user_input + "'")

# fixed — the value is bound through a placeholder
cursor.execute("SELECT * FROM members WHERE member_id = ?", (user_input,))

PHP (PDO — common in small SACCO web apps):

// vulnerable
$db->query("SELECT * FROM members WHERE member_id = '" . $_GET['id'] . "'");

// fixed — prepare, then bind
$stmt = $db->prepare("SELECT * FROM members WHERE member_id = ?");
$stmt->execute([$_GET['id']]);

Java (JDBC):

// vulnerable
stmt.executeQuery("SELECT * FROM members WHERE member_id = '" + id + "'");

// fixed — PreparedStatement with a ? placeholder
PreparedStatement ps = conn.prepareStatement("SELECT * FROM members WHERE member_id = ?");
ps.setString(1, id);
ps.executeQuery();

The placeholder differs by language (?, %s, :name), but the idea is identical everywhere: never build the SQL string by hand from user input.

4. Extra hardening (defence in depth)
  • Validate input — if an id must be a number, reject anything that isn't. This isn't a substitute for parameterized queries, but it helps.
  • Least privilege — the database account the app uses should only be able to do what it needs (e.g. read members, not drop tables).
  • Don't show raw errors — database error messages hand attackers clues. Log them; show the user a friendly message.

Note: this project's training focuses on the main fix — parameterized queries — because that's what removes the vulnerability itself.

5. How to spot it when reviewing code
  • Look for a SQL string being built with +, an f-string, .format(), or % around a request value.
  • Check whether there's a placeholder (? / %s / :name) and the value passed separately — if so, it's safe.
  • Any value that comes from the user (URL, form, cookie, header) and reaches a query is a candidate — trace it.
